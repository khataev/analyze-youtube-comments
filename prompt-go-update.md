# Задача: перевести backend-go на Postgres и общую инфраструктуру

Реализация в `backend-go/` уже готова и работает по первой версии `../prompt-go.md`. С тех пор эталонная Python-версия (`../backend-python/`) изменилась, а промпт обновлён. Нужно привести Go-версию к новому состоянию, **не переписывая её с нуля**: структура пакетов, asynq, обработка ошибок и всё остальное, что не перечислено ниже, остаются как есть.

Перед началом:
- прочитай обновлённый `../prompt-go.md`: разделы «Общая инфраструктура», «Хранение задач», «Тесты» и новые пункты в «Что мы уже выучили»;
- посмотри, как это сделано в Python-версии: `git -C ../backend-python log --oneline` и её README.

## Что изменить

### 1. Общая инфраструктура вместо своего Redis

- Redis и Postgres теперь общие для всех реализаций: `../docker-compose.yml`, сеть `ayc-infra`, пользователь и пароль `app`. Распределение баз — в `../README.md`.
- Для Go: база `analysis_go`, тестовая `analysis_go_test`, Redis DB `1` (`REDIS_URL=redis://localhost:6379/1`).
- В `docker-compose.yml` убрать сервис `redis`, подключиться к `ayc-infra` как к внешней сети. Добавить одноразовый сервис `migrate` (создать базу, если её нет, и применить миграции), `api` и `worker` стартуют после его успешного завершения.
- Поправить `Makefile`: комментарии «нужен Redis» и «внешние сервисы не нужны», цель `docker-up`. Добавить цели для создания базы и миграций.

### 2. Хранение задач в Postgres

- Таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`, `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно.
- `RedisRepository` заменить реализацией на Postgres за тем же интерфейсом `TaskStore`: сервис и анализатор меняться не должны. Каждая операция — короткая транзакция.
- Библиотеку выбери и обоснуй. Ориентиры: `pgx` (+ `sqlc`), миграции `goose` или `golang-migrate`.
- База создаётся самим backend, если её нет, — аналог `rails db:create` (в Python `python -m app.db.create`). В Postgres нет `CREATE DATABASE IF NOT EXISTS`.
- Ошибки соединения с БД → `ErrStorageUnavailable` (503), как сейчас для Redis. `/health` проверяет и Postgres, и Redis.
- Конфигурация:
  - `TASK_TTL_SECONDS` удалить (config, тесты, `.env.example`, README);
  - добавить `DATABASE_URL` в формате, принятом в Go;
  - создание базы и миграции не должны требовать `YOUTUBE_API_KEY` и ключа LLM, а сейчас `YOUTUBE_API_KEY` обязателен для всего `Config`. Раздели конфигурацию так, чтобы командам БД хватало только `DATABASE_URL`.
- Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскируются. При старте API и воркера логируется, к каким Redis и Postgres подключились.
- Redis остаётся только очередью asynq.

### 3. Тесты на настоящем Postgres

- Тесты репозитория и всё, что ходит в хранилище, работают с базой `analysis_go_test` в общем Postgres, а не с miniredis. miniredis остаётся только там, где он нужен для очереди.
- Схема накатывается миграциями один раз на прогон (`TestMain`), каждый тест выполняется в транзакции с откатом. Если Postgres не запущен, прогон останавливается с понятным сообщением, а не десятком одинаковых ошибок соединения.
- SQLite и in-memory подмены БД не использовать.

### 4. Домен, связность и имена

Сейчас анализатор знает про пакет `youtube`: интерфейсы `CommentSource` и `Classifier` используют `youtube.Comment`, а `handleFailure` проверяет `*youtube.Error`. В Python-версии это убрали:
- `Comment` — доменный тип пакета `analysis`. Клиент YouTube возвращает его сам, то есть `youtube` импортирует `analysis`, а не наоборот.
- Доменная ошибка источника (в Python — `CommentSourceError`) объявлена в `analysis`. Ошибки YouTube оборачивают её (`errors.Is`/`errors.As`), и анализатор не импортирует `youtube`.
- `CommentOut` из доменной модели убрать: результат задачи хранит доменный `Comment`, а форма JSON-ответа описывается в слое HTTP.

Именование:
- В Go имя пакета — часть имени, поэтому доменная сущность может остаться `analysis.Task`: это и есть «чистое имя».
- Модель хранения отделена от домена (например, сгенерированная `sqlc` структура или неэкспортируемая `taskRow`), репозиторий переводит одно в другое.
- Типы HTTP-ответов уже отдельные (`startResponse`, `statusResponse`), их оставь. Подбери им и вложенному комментарию единый шаблон имён.

## Как работать

1. Сначала предложи план: библиотеку БД и миграций, где живёт создание базы, как разделить конфигурацию, как устроить транзакционные тесты. Дождись моего согласия.
2. Делай изменения отдельными логическими шагами, примерно по разделам выше, чтобы их можно было ревьюить и коммитить по отдельности. После каждого шага прогоняй тесты и `golangci-lint`.
3. Обнови README: хранение, миграции, запуск с общей инфраструктурой, тестовая база.
4. В конце проверь живой запуск через Docker: `migrate` + API + воркер + общие Redis и Postgres, задача доходит до финального статуса и лежит в таблице. Покажи логи.
