# Задача: реализация backend на Java + Spring Boot

Сделай в папке `backend-java/` реализацию backend-сервиса на **Java и Spring Boot**. Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель не в минимальном количестве кода, а в том, чтобы показать, как идиоматично устраивают такие сервисы на Spring Boot. Эту реализацию я буду сравнивать с версиями на Python, Go, Node, Rust, Kotlin и .NET.

**Обо мне:** я знаю Ruby/Rails (Sidekiq, `rails c`) и Python/FastAPI. Java и Spring для меня новые. Поэтому:
- объясняй «магию» Spring коротко, в README и в комментариях, с аналогиями из Rails/FastAPI там, где они помогают:
  - автоконфигурацию;
  - бины и DI;
  - профили;
  - аннотации, которые меняют поведение (`@Transactional`, `@Validated` и т.п.);
- предпочитай явный и читаемый код: не используй аннотацию там, где пять строк явного кода понятнее;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Поля JSON в `snake_case`. У Jackson по умолчанию `camelCase`, настрой.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`. Spring по умолчанию отдаёт `400`, поменяй;
  - кривой `task_id` → `422`;
  - неизвестная задача → `404`, в теле `"detail": "Task not found"`;
  - Postgres или Redis недоступен → `503`, в теле `"detail": "Storage is unavailable"`.

  Формат `ProblemDetail` (RFC 9457) допустим: поле `detail` там уже есть, дополнительные поля не мешают.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- `/health` по контракту — отдельный простой эндпоинт. Actuator можно подключить дополнительно.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_java`, тестовая — `analysis_java_test`.
- Номер БД Redis — `4` (`REDIS_URL=redis://localhost:6379/4`).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код: реализация должна выглядеть как нормальный современный Spring Boot-проект.

- **Пакеты по доменам (package-by-feature):** `analysis`, `youtube`, `llm`, общая инфраструктура. Не делай верхнеуровневые `controllers/`, `services/`, `repositories/`. Для контроля границ модулей оцени Spring Modulith и предложи, стоит ли он того.
- **Слои и направление зависимостей:** `controller → service → repository / clients`.
  - Контроллер знает только HTTP.
  - Сервис ничего не знает про HTTP, БД и Redis.
  - Сервис зависит от **интерфейсов** (очередь задач, источник комментариев, классификатор, хранилище задач).
  - Внедрение только через конструктор, без field injection.
- **Модели.** `record` для DTO и значений, `enum` для статусов и категорий. Внутренние модели отделены от DTO ответа.
- **Валидация на границе.** Bean Validation для входа и `@ConfigurationProperties` + `@Validated` для конфигурации: приложение падает при старте с понятной ошибкой.
- **Ошибки:**
  - доменные исключения сервисов (не HTTP-исключения) переводятся в коды через `@RestControllerAdvice`;
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`.
- **Конкурентность.** Используй virtual threads (Java 21+) и обычный блокирующий стиль кода. Объясни в README, почему здесь не нужен реактивный стек (WebFlux).
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - Можно собрать один артефакт с профилями `api` и `worker`: у воркера web отключён (`web-application-type=none`). Можно сделать multi-module сборку. Предложи и обоснуй.
  - Задача не должна теряться при падении воркера. В Python-версии это слабое место: `BRPOP` удаляет сообщение сразу при получении.
  - Ожидаемый вариант — Redis Streams с consumer groups через Spring Data Redis (`StreamMessageListenerContainer`, ack, повторная доставка зависших сообщений). Если выберешь другое (Redisson и т.п.), аргументируй.
  - Нужны повторные попытки с ограничением.
- **Хранение задач — Postgres**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`,
  `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет).
  Схема задаётся миграциями, принятыми в стеке. Библиотеку доступа к БД выбери и обоснуй, ориентиры: Spring Data JDBC или JPA, миграции Flyway или Liquibase.
  Redis — только очередь.
  - Доменная сущность отделена от модели хранения: сервисы работают с доменной `AnalysisTask`
    и не знают о БД, репозиторий переводит её в модель хранения и обратно.
  - Каждая операция репозитория — своя короткая транзакция: обработка задачи в воркере длится
    минутами, держать соединение всё это время незачем.
- **Внешние вызовы:**
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429), понятные ошибки для 404, 403 и 400, `RestClient` с таймаутами;
  - LLM: структурированный ответ по схеме с валидацией, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** числа одновременных запросов.
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. Оцени Spring AI (`ChatClient` со структурированным выводом, OpenAI-совместимый endpoint). Держи провайдера за своим интерфейсом.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала». Логи структурированные (встроенный structured logging Spring Boot или logback JSON), `task_id` в MDC.
- **Ожидание сообщений в очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Сверь таймаут команд Lettuce с таймаутом опроса стрима.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом (в Python — `AnalysisTaskOrm`);
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенная `CommentSchema`.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
  Если в стеке принят другой суффикс, следуй ему, но единообразно.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот.
  Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника
  (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены
  отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальная LTS-версия Java и актуальный Spring Boot.
- Gradle (Kotlin DSL) или Maven: выбери и обоснуй.
- Библиотеки выбирай сам, предпочитая стандарт экосистемы Spring. Каждый выбор кратко обоснуй в README.
- Тесты:
  - **основной набор** (YouTube, LLM и очередь подменяются): unit-тесты разбора URL, клиента YouTube (WireMock или `MockRestServiceServer`), сервиса (с фейками интерфейсов), группировки результатов; срез `@WebMvcTest` для HTTP;
  - БД в тестах — настоящий Postgres из общей инфраструктуры (база `analysis_java_test`), как в Rails.
    Схема накатывается миграциями один раз на прогон (заодно проверяются сами миграции), каждый тест
    выполняется в транзакции с откатом. Если Postgres не запущен, прогон сразу останавливается
    с понятным сообщением. SQLite и in-memory подмены БД не используй: они скрывают различия СУБД.
  - Testcontainers допустим для отдельного интеграционного набора (путь «API → очередь → воркер» с настоящим Redis), который запускается отдельной командой.
- Форматирование и статический анализ: Spotless и Error Prone или Checkstyle, сборка падает на нарушениях.
- Команды сборки и запуска: `run-api`, `run-worker`, `test`, `integrationTest`, `lint` в виде задач Gradle или `Makefile`.
- Многоэтапный `Dockerfile` (layered jar или jlink) и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта с пояснением каждого пакета;
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение ключевых решений с Python-версией.
  - Отдельно: как исследовать работающее приложение интерактивно, по аналогии с `rails c` (например, `jshell` с classpath проекта или Actuator-эндпоинты).

## Как работать

1. Сначала предложи структуру, выбор библиотек и подход к очереди. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты и линтеры.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
