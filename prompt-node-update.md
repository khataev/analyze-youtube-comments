# Задача: перевести backend-node на Postgres и общую инфраструктуру

Реализация в `backend-node/` уже готова и работает по первой версии `../prompt-node.md`. С тех пор эталонная Python-версия (`../backend-python/`) изменилась, а промпт обновлён. Нужно привести Node-версию к новому состоянию, **не переписывая её с нуля**: модули Nest, BullMQ, zod-валидация, `DomainError`, порты и всё остальное, что не перечислено ниже, остаются как есть.

Перед началом:
- прочитай обновлённый `../prompt-node.md`: разделы «Общая инфраструктура», «Хранение задач», «Тесты» и новые пункты в «Что мы уже выучили»;
- посмотри, как это сделано в Python-версии: `git -C ../backend-python log --oneline` и её README.

## Что изменить

### 1. Общая инфраструктура вместо своего Redis

- Redis и Postgres теперь общие для всех реализаций: `../docker-compose.yml`, сеть `ayc-infra`, пользователь и пароль `app`. Распределение баз — в `../README.md`.
- Для Node: база `analysis_node`, тестовая `analysis_node_test`, Redis DB `2` (`REDIS_URL=redis://localhost:6379/2`).
- В `docker-compose.yml` убрать сервис `redis`, подключиться к `ayc-infra` как к внешней сети. Добавить одноразовый сервис `migrate` (создать базу, если её нет, и применить миграции), `api` и `worker` стартуют после его успешного завершения.
- Добавить скрипты в `package.json`: создание базы и миграции.

### 2. Хранение задач в Postgres

- Таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`, `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно.
- `TaskRepository` переписать на Postgres с тем же публичным интерфейсом: `AnalysisService` и `CommentAnalyzer` меняться не должны. Каждая операция — короткая транзакция.
- Библиотеку выбери и обоснуй: Prisma, Drizzle, MikroORM или TypeORM. В Nest-проектах TypeORM встречается чаще всего — оцени, а не бери по инерции. Учитывай удобство транзакционных тестов (см. раздел 3).
- База создаётся самим backend, если её нет, — аналог `rails db:create` (в Python `python -m app.db.create`). В Postgres нет `CREATE DATABASE IF NOT EXISTS`.
- Ошибки соединения с БД → `StorageUnavailableError` (503), как сейчас для Redis. Health-check (terminus) проверяет и Postgres, и Redis.
- Комментарий в `domain/task-record.ts` про общий с Python формат JSON в Redis больше не актуален: у реализаций разные базы. Сериализацию в Redis-формат убрать.
- Конфигурация:
  - `TASK_TTL_SECONDS` удалить как TTL задач (`env.schema.ts`, `app.config.ts`, тесты, `.env.example`, README);
  - он же сейчас задаёт `removeOnComplete`/`removeOnFail` для джобов BullMQ. Это отдельная настройка — сколько хранить служебные данные очереди в Redis. Задай её отдельно (константа или своя переменная) и объясни выбор;
  - добавить `DATABASE_URL`;
  - создание базы и миграции не должны требовать `YOUTUBE_API_KEY` и ключа LLM. Сейчас `env.schema.ts` требует `YOUTUBE_API_KEY` для любого запуска: раздели схему так, чтобы командам БД хватало только `DATABASE_URL`.
- Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскируются (`redact-url.ts`). При старте API и воркера логируется, к каким Redis и Postgres подключились.
- Redis остаётся только очередью BullMQ.

### 3. Тесты на настоящем Postgres

- Тесты репозитория и e2e-тесты, которые ходят в хранилище, работают с базой `analysis_node_test` в общем Postgres, а не с fake Redis. Fake Redis остаётся только там, где он нужен для очереди.
- Схема накатывается миграциями один раз на прогон (global setup Vitest). Каждый тест изолирован транзакцией с откатом.
  - Если выбранная библиотека делает это неудобным (например, у Prisma нет вложенных транзакций), допустима очистка таблиц между тестами. Обоснуй выбор.
- Если Postgres не запущен, прогон останавливается с понятным сообщением, а не десятком одинаковых ошибок соединения.
- SQLite и in-memory подмены БД не использовать.

### 4. Имена

- `TaskRecord` → `AnalysisTask`: доменная сущность получает чистое имя. Слова «record» и «row» для доменных объектов не используем, в терминах БД это синонимы строки. `newTaskRecord` и прочие производные имена — туда же.
- Модель хранения (entity, сгенерированный тип или схема таблицы — зависит от библиотеки) отделена от домена и имеет суффикс, принятый в выбранной библиотеке. Репозиторий переводит одно в другое.
- DTO ответов уже названы по роли (`TaskCreatedResponse`, `TaskStatusResponse`) — хорошо. Во вложенном комментарии ответа не используй суффикс `Schema`, как в Python (`CommentSchema`): в zod-коде он уже означает zod-схему (`commentSchema`), и получится путаница. Выбери имя, которое не конфликтует, и примени его единообразно.

## Как работать

1. Сначала предложи план: библиотеку БД и миграций, где живёт создание базы, как разделить конфигурацию, как устроить изоляцию тестов, что делать с хранением джобов BullMQ. Дождись моего согласия.
2. Делай изменения отдельными логическими шагами, примерно по разделам выше, чтобы их можно было ревьюить и коммитить по отдельности. После каждого шага прогоняй `test`, `lint` и `typecheck`.
3. Обнови README: хранение, миграции, запуск с общей инфраструктурой, тестовая база.
4. В конце проверь живой запуск через Docker: `migrate` + API + воркер + общие Redis и Postgres, задача доходит до финального статуса и лежит в таблице. Покажи логи.
