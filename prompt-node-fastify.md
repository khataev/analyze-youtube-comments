# Задача: реализация backend на Node.js + Fastify (форк Nest-версии)

Сделай в папке `backend-node-fastify/` реализацию backend-сервиса на **Fastify** и TypeScript. Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Это форк `../backend-node/` (NestJS): цель — сравнить, как тот же сервис выглядит без Nest. Поэтому:
- код, не зависящий от фреймворка, бери из Nest-версии (копированием, без импорта между папками) и адаптируй: доменные типы и ошибки, порты, разбор URL, группировка результатов, клиент YouTube, LLM-классификатор, zod-схемы, логика очереди BullMQ;
- заново пиши всё, что в Nest-версии делал фреймворк: сборку приложения, DI, модули, pipes, filters, lifecycle hooks, health-check, точки входа;
- Nest-версия может ещё хранить задачи в Redis: её переводят на Postgres по `../prompt-node-update.md`. Здесь сразу делай Postgres по требованиям ниже. Если к началу работы Nest-версия уже переведена, возьми её слой хранения за основу.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель — показать, как идиоматично устраивают такие сервисы на Fastify, а не воссоздать Nest поверх Fastify.

**Обо мне:** я знаю Ruby/Rails (Sidekiq, `rails c`) и Python/FastAPI, видел Nest-версию этого сервиса. Fastify для меня новый. Поэтому:
- объясняй ключевые механизмы Fastify коротко, в README и в комментариях, с аналогиями из Rails/FastAPI/Nest там, где они помогают:
  - плагины и инкапсуляция контекста, `fastify-plugin`;
  - декораторы (`decorate`, `decorateRequest`) — это не декораторы TypeScript;
  - хуки жизненного цикла запроса и приложения;
  - схемы маршрутов: валидация входа и сериализация ответа;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Поля в JSON в `snake_case`, как в Python-версии, даже если внутри кода используется `camelCase`.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`. Fastify по умолчанию отвечает на ошибки валидации `400`, поменяй;
  - кривой `task_id` → `422`;
  - неизвестная задача → `404 {"detail": "Task not found"}`;
  - Postgres или Redis недоступен → `503 {"detail": "Storage is unavailable"}`.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_node_fastify`, тестовая — `analysis_node_fastify_test`.
- Номер БД Redis — `10` (`REDIS_URL=redis://localhost:6379/10`).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

- **Организация по доменам**, как в Nest-версии, но средствами Fastify:
  - `analysis`: маршруты (плагин), сервисы, репозиторий, процессор очереди;
  - `youtube`, `llm`: внешние клиенты;
  - инфраструктура: config, БД, Redis, health.

  Домен регистрируется как плагин с префиксом. Где нужна инкапсуляция, а где `fastify-plugin` — реши и объясни.
- **Слои и направление зависимостей:** `routes → service → repository / clients`.
  - Маршруты знают только HTTP.
  - Сервис ничего не знает про Fastify, БД и Redis.
  - Сервис зависит от **портов** (очередь задач, источник комментариев, классификатор), а не от реализаций.
- **DI без контейнера Nest.** Ожидаемый вариант — явный composition root: функция собирает граф зависимостей из конфигурации и передаёт его в `buildApp(deps)` и в воркер. Тесты передают туда фейки — аналог `dependency_overrides` в FastAPI и `overrideProvider` в Nest. Ресурсы приложения доступны маршрутам через `decorate` с типизацией (`declare module 'fastify'`). Если считаешь, что нужен контейнер (например, `@fastify/awilix`), аргументируй.
- **Схемы маршрутов.** Вход валидируется схемой маршрута, ответ сериализуется по схеме ответа: так же лишние поля не утекают клиенту. Варианты:
  - zod через `fastify-type-provider-zod` — переиспользуются схемы Nest-версии;
  - TypeBox (`@fastify/type-provider-typebox`) — родной для Fastify JSON Schema.

  Выбери и обоснуй. OpenAPI через `@fastify/swagger` и `/docs`.
- **Ошибки:**
  - доменные ошибки переводятся в HTTP-коды в одном месте: `setErrorHandler`, плюс `setNotFoundHandler`;
  - ошибки валидации → `422`;
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`.
- **Конфигурация** читается и валидируется один раз при старте, при ошибке процесс падает сразу с понятным сообщением. Она нужна и API, и воркеру, который Fastify не поднимает, поэтому не завязывай её только на Fastify-плагин (`@fastify/env`). Без `process.env` по всему коду.
- **Жизненный цикл.** Ресурсы (пул БД, Redis, HTTP-клиенты) закрываются в `onClose`. Graceful shutdown по SIGTERM: `app.close()`, например через `close-with-grace`.
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - BullMQ, как в Nest-версии. Задача не должна теряться при падении воркера. В Python-версии это слабое место: `BRPOP` удаляет сообщение сразу при получении.
  - Воркер — отдельная точка входа без HTTP-сервера. Он использует тот же composition root. Решать, создавать ли в воркере экземпляр Fastify без `listen` ради плагинов, тебе — объясни выбор.
  - API только ставит задачи.
- **Хранение задач — Postgres**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`, `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет). Схема задаётся миграциями. Библиотеку доступа к БД выбери и обоснуй; если Nest-версия уже переведена на Postgres, по умолчанию возьми ту же — так сравнение будет честнее. Redis — только очередь.
  - Доменная сущность отделена от модели хранения: сервисы работают с доменной `AnalysisTask` и не знают о БД, репозиторий переводит её в модель хранения и обратно.
  - Каждая операция репозитория — своя короткая транзакция: обработка задачи в воркере длится минутами, держать соединение всё это время незачем.
- **Внешние вызовы:**
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429), понятные ошибки для 404, 403 и 400, таймауты;
  - LLM: структурированный ответ по схеме с валидацией, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** числа одновременных запросов.
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. Держи провайдера за абстракцией.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать. У pino для этого есть опция `redact`.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала». В Fastify логгер pino встроен: в маршрутах — `request.log`, в воркере — дочерний логгер с `task_id`.
- **Блокирующее ожидание очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. У BullMQ и ioredis свои требования к настройкам соединения воркера: возьми решение из Nest-версии и проверь его.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом, принятым в выбранной библиотеке;
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`. Для вложенного комментария не используй суффикс `Schema`, как в Python (`CommentSchema`): в zod-коде он означает zod-схему.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот. Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальная LTS-версия Node.js, TypeScript в strict-режиме, тот же пакетный менеджер, что в Nest-версии. Как запускать TypeScript в разработке (`tsx` или встроенное в Node удаление типов), выбери и обоснуй.
- ESLint и Prettier.
- **Тесты.** YouTube, LLM и очередь подменяются. БД в тестах — настоящий Postgres из общей инфраструктуры (база `analysis_node_fastify_test`), как в Rails. Схема накатывается миграциями один раз на прогон, каждый тест изолирован транзакцией с откатом; если выбранная библиотека делает это неудобным, допустима очистка таблиц между тестами — обоснуй. Если Postgres не запущен, прогон сразу останавливается с понятным сообщением. SQLite и in-memory подмены БД не используй.

  Vitest:
  - unit-тесты разбора URL, клиента YouTube (с моком HTTP), сервиса (с фейками портов), группировки результатов;
  - HTTP-тесты через `app.inject()` — без поднятия сервера и без supertest;
  - тест пути «API → очередь → процессор».
- Скрипты в `package.json`: `start:api`, `start:worker`, их dev-варианты с watch, `db:create`, `db:migrate`, `test`, `lint`, `typecheck`.
- Многоэтапный `Dockerfile` и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта с пояснением каждого плагина и модуля;
  - как запустить локально и в Docker;
  - как проверить;
  - **сравнение с Nest-версией**: что давал Nest (модули, DI, декораторы, pipes, filters, lifecycle hooks, `@nestjs/terminus`, `repl`) и чем это заменено здесь, сколько кода и зависимостей ушло или прибавилось, где Fastify проще, а где пришлось писать руками;
  - кратко — сравнение с Python-версией.
  - Отдельно: как открыть REPL с загруженным приложением (аналог `rails c`). Встроенного `repl`, как у Nest, у Fastify нет: сделай скрипт на `node:repl`, который собирает composition root и кладёт зависимости в контекст, с поддержкой `await`.

## Как работать

1. Сначала предложи структуру каталогов, выбор библиотек (схемы, БД, DI) и список того, что переносится из Nest-версии как есть, а что пишется заново. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты, линтер и проверку типов.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
