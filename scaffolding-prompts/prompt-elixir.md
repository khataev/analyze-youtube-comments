# Задача: реализация backend на Elixir + Phoenix

Сделай в папке `backend-elixir/` реализацию backend-сервиса на **Elixir и Phoenix** (только API, без HTML и ассетов). Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель — показать идиоматичный Elixir/OTP-сервис. Эту реализацию я буду сравнивать с версиями на Python, Go, Node, Rust, Java, Kotlin, .NET, Sinatra и Roda.

**Обо мне:** Ruby и Rails я знаю хорошо (Sidekiq, `rails c`), Python/FastAPI тоже. Elixir для меня новый. Поэтому:
- объясняй неочевидное коротко, в README и в комментариях, с аналогиями из Ruby/Rails там, где они помогают:
  - pattern matching и `with`;
  - процессы, супервизоры и «let it crash»;
  - behaviours как интерфейсы;
  - контексты Phoenix;
  - иммутабельность.

  Синтаксис похож на Ruby, а модель исполнения совсем другая: делай акцент на ней;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если хранилище недоступно |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`;
  - невалидное тело или кривой `task_id` → `422`;
  - неизвестная задача → `404 {"detail": "Task not found"}`;
  - хранилище недоступно → `503 {"detail": "Storage is unavailable"}`.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_elixir`, тестовая — `analysis_elixir_test`.
- Номер БД Redis — `9` (`REDIS_URL=redis://localhost:6379/9`), если Redis используется (для Oban он не нужен).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код: реализация должна выглядеть как нормальный Elixir-проект.

- **Контексты Phoenix как доменные границы:**
  - `Analysis`: публичный API контекста, хранилище задач, задача;
  - `YouTube`, `LLM`: внешние клиенты.

  Web-слой (`router`, контроллеры, JSON-представления, `FallbackController`) знает только HTTP и вызывает публичные функции контекстов.
- **Зависимости через behaviours.** Очередь, источник комментариев, классификатор и хранилище задач — behaviours. Реализация выбирается через конфигурацию, в тестах подменяется Mox.
- **Данные и валидация.**
  - Структуры (`defstruct` с `@enforce_keys`) и typespecs;
  - вход валидируется до контекста (embedded Ecto schemas и changesets);
  - результаты возвращаются как `{:ok, _}` / `{:error, _}`, ошибки — через `with` и `FallbackController`;
  - внутренние детали не утекают клиенту.
- **Конфигурация.** `config/runtime.exs` из переменных окружения с проверкой при старте: при ошибке приложение падает сразу с понятным сообщением.
- **Супервизия и жизненный цикл.** Дерево супервизии приложения явно описано. Соединения и пулы — дочерние процессы супервизора. Graceful shutdown.
- **Фоновая обработка и надёжность.**
  - Требование то же, что в эталоне: задача переживает рестарт и деплой, не теряется при падении обработчика, есть повторные попытки с ограничением, после исчерпания попыток — статус `failed`.
  - В Python-версии слабое место — `BRPOP`, который удаляет сообщение сразу при получении.
  - На BEAM процесс-обработчик дёшев, но процессы живут в памяти узла. Поэтому для надёжности всё равно нужно персистентное хранилище задач.
  - Ожидаемый вариант — **Oban**: стандарт де-факто, хранит задачи в том же Postgres, где таблица `analysis_tasks`. Отклонения от общей инфраструктуры больше нет, а создание записи и постановку задачи можно сделать в одной транзакции — у Redis-очередей такого нет. Объясни, что это даёт.
  - Альтернативы, если аргументируешь: **Exq** (Redis, формат совместим с Sidekiq) или собственная очередь на Redis Streams.
  - «API и воркер раздельно» здесь можно реализовать идиоматично для Elixir: один релиз, роль узла задаётся конфигурацией (на API-узлах очереди не обрабатываются). Объясни, чем это отличается от отдельных процессов в Python и Ruby.
- **Хранение задач — Postgres через Ecto**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`, `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет). Схема — Ecto-миграциями, база создаётся `mix ecto.create`.
  - В Phoenix Ecto-схема обычно и есть структура контекста, а граница проходит по публичному API контекста. Отдельная доменная структура поверх Ecto-схемы, как в Python-версии (`AnalysisTask` и `AnalysisTaskOrm`), здесь может быть избыточной: реши и обоснуй. Главное, чтобы web-слой и behaviours не зависели от Ecto напрямую.
  - Каждая операция — своя короткая транзакция: обработка задачи длится минутами, держать соединение всё это время незачем.
- **Внешние вызовы:**
  - YouTube через `Req`: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки только для временных ошибок (сеть, 5xx, 429; проверь политику retry в Req), понятные ошибки для 404, 403 и 400, таймауты;
  - LLM: структурированный ответ по схеме с валидацией (например, InstructorLite с Ecto-схемой или OpenAI-совместимый клиент), комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** через `Task.async_stream` с `max_concurrency`.
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. DeepSeek совместим с OpenAI API. Держи провайдера за behaviour.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - обработчик: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте: к каким Postgres и Redis (если используется) подключились (пароль замаскирован) и какие очереди обрабатывает узел.

  Это позволяет сразу отличить «обработчик не запущен» от «задача упала».
  - `task_id` в `Logger.metadata`;
  - метаданные привязаны к процессу и сами не переходят в `Task.async_stream`: учти это.
- **Ожидание сообщений в очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Если используется Redis, проверь таймауты блокирующих команд в Redix.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом (в Python — `AnalysisTaskOrm`);
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенная `CommentSchema`.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
  Если в стеке принят другой суффикс, следуй ему, но единообразно.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот.
  Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника
  (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены
  отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальные стабильные версии Elixir, Erlang/OTP и Phoenix.
- Библиотеки выбирай сам, предпочитая общепринятые в экосистеме. Каждый выбор кратко обоснуй в README.
- Тесты на ExUnit. YouTube и LLM подменяются, а БД — настоящий Postgres из общей инфраструктуры (база `analysis_elixir_test`), как в Rails. Изоляцию даёт `Ecto.Adapters.SQL.Sandbox`: каждый тест работает в транзакции с откатом — это то же, что в Python-версии сделано вручную. Если Postgres не запущен, прогон сразу останавливается с понятным сообщением. Наборы:
  - unit-тесты разбора URL, клиента YouTube (`Req.Test` или Bypass), контекста (Mox для внешних клиентов), группировки результатов;
  - тесты контроллеров через `ConnTest`;
  - путь «API → очередь → обработчик» через тестовый режим очереди (например, `Oban.Testing`).
- `mix format`, Credo (strict), Dialyzer: без замечаний.
- `iex -S mix` — прямой аналог `rails c`. Покажи в README, как пользоваться им с этим проектом и как подключиться к работающему релизу (`bin/<app> remote`).
- Mix-алиасы или `Makefile`: `server`, `worker` (если роли разделены), `test`, `lint`.
- Многоэтапный `Dockerfile` на `mix release` и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта и дерево супервизии;
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение ключевых решений с Python-версией и с Rails/Sidekiq.

1. Сначала предложи структуру, выбор библиотек и, главное, подход к очереди и хранилищу. Дождись моего согласия.

3. В конце проверь живой запуск: API + обработчик + Postgres, задача доходит до финального статуса. Покажи логи.
