# Задача: реализация backend на Kotlin + Ktor

Сделай в папке `backend-kotlin/` реализацию backend-сервиса на **Kotlin и Ktor**, с корутинами. Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель не в минимальном количестве кода, а в том, чтобы показать идиоматичный Kotlin-сервис.

Почему Ktor: Spring Boot уже есть в Java-версии. Здесь интересно сравнить «Kotlin-нативный» подход:
- корутины и structured concurrency;
- `kotlinx.serialization`;
- явная сборка приложения вместо автоконфигурации.

Эту реализацию я буду сравнивать с версиями на Python, Go, Node, Rust, Java и .NET.

**Обо мне:** я знаю Ruby/Rails (Sidekiq, `rails c`) и Python/FastAPI. Kotlin для меня новый. Поэтому:
- объясняй неочевидные решения коротко, в README и в комментариях, с аналогиями из Ruby/Python там, где они помогают:
  - корутины, `suspend`, scopes и отмену;
  - sealed-классы;
  - null-safety;
  - плагины Ktor;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Поля JSON в `snake_case`.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`;
  - кривой `task_id` → `422`;
  - неизвестная задача → `404 {"detail": "Task not found"}`;
  - Postgres или Redis недоступен → `503 {"detail": "Storage is unavailable"}`.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_kotlin`, тестовая — `analysis_kotlin_test`.
- Номер БД Redis — `5` (`REDIS_URL=redis://localhost:6379/5`).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код: реализация должна выглядеть как нормальный Kotlin-проект.

- **Структура.** Multi-module Gradle (Kotlin DSL) с version catalog, например:
  - доменный модуль без зависимостей от Ktor, БД и Redis;
  - инфраструктура;
  - приложения `api` и `worker`.

  Если для этого размера это избыточно, предложи альтернативу с обоснованием.
- **Пакеты по доменам:** `analysis`, `youtube`, `llm`, общая инфраструктура.
- **Слои и направление зависимостей:** `routes → service → repository / clients`.
  - Маршруты знают только HTTP.
  - Сервис ничего не знает про HTTP, БД и Redis.
  - Сервис зависит от **интерфейсов** (очередь задач, источник комментариев, классификатор, хранилище задач).
- **DI.** Ручная сборка в composition root, Koin или DI-плагин Ktor: выбери и обоснуй. Без глобального состояния.
- **Модели.**
  - `data class` и `@JvmInline value class` для `VideoId` и `TaskId`;
  - `enum` или `sealed` для статусов, категорий и доменных ошибок;
  - внутренние модели отделены от DTO ответа.
- **Ошибки:**
  - доменные ошибки переводятся в HTTP-коды в одном месте (плагин `StatusPages`);
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`;
  - отмена корутины (`CancellationException`) не проглатывается как обычная ошибка.
- **Конфигурация** типизированная и валидируемая при старте (например, Hoplite или собственный слой поверх env): при ошибке процесс падает сразу с понятным сообщением.
- **Жизненный цикл.**
  - ресурсы создаются один раз и закрываются при остановке;
  - graceful shutdown;
  - structured concurrency: фоновые корутины привязаны к scope приложения, а не к `GlobalScope`.
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - Корутины дают асинхронность дёшево. Но отдельный воркер нужен ради надёжности: задачи переживают рестарт и деплой API, API и обработка масштабируются независимо.
  - Задача не должна теряться при падении воркера. В Python-версии это слабое место: `BRPOP` удаляет сообщение сразу при получении.
  - Ожидаемый вариант — Redis Streams с consumer groups (ack, повторная доставка зависших сообщений) через Lettuce с корутинным API. Если выберешь другое, аргументируй.
  - Нужны повторные попытки с ограничением.
- **Хранение задач — Postgres**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`,
  `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет).
  Схема задаётся миграциями, принятыми в стеке. Библиотеку доступа к БД выбери и обоснуй, ориентиры: Exposed или jOOQ, миграции Flyway.
  Redis — только очередь.
  - Доменная сущность отделена от модели хранения: сервисы работают с доменной `AnalysisTask`
    и не знают о БД, репозиторий переводит её в модель хранения и обратно.
  - Каждая операция репозитория — своя короткая транзакция: обработка задачи в воркере длится
    минутами, держать соединение всё это время незачем.
- **Внешние вызовы** через Ktor Client:
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429; плагин `HttpRequestRetry`), понятные ошибки для 404, 403 и 400, таймауты;
  - LLM: структурированный ответ по схеме с проверкой при десериализации, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** (`Semaphore` или ограниченный `Dispatcher`).
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. DeepSeek совместим с OpenAI API, так что достаточно OpenAI-совместимого клиента с настраиваемым base URL. Можешь оценить Koog (JetBrains). Держи провайдера за интерфейсом.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала».
  - Логи структурированные, `task_id` в MDC.
  - MDC сам не переносится между корутинами: используй `MDCContext`.
- **Ожидание сообщений в очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Сверь таймаут команд Lettuce с блокирующим чтением стрима.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом (в Python — `AnalysisTaskOrm`);
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенная `CommentSchema`.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
  Если в стеке принят другой суффикс, следуй ему, но единообразно.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот.
  Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника
  (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены
  отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальные стабильные версии Kotlin, Ktor и JDK (LTS).
- Библиотеки выбирай сам, предпочитая общепринятые в Kotlin-экосистеме. Каждый выбор кратко обоснуй в README.
- Тесты:
  - **основной набор** (YouTube, LLM и очередь подменяются): unit-тесты разбора URL, клиента YouTube (Ktor `MockEngine`), сервиса (с фейками интерфейсов и `runTest`), группировки результатов; HTTP через `testApplication`;
  - БД в тестах — настоящий Postgres из общей инфраструктуры (база `analysis_kotlin_test`), как в Rails.
    Схема накатывается миграциями один раз на прогон (заодно проверяются сами миграции), каждый тест
    выполняется в транзакции с откатом. Если Postgres не запущен, прогон сразу останавливается
    с понятным сообщением. SQLite и in-memory подмены БД не используй: они скрывают различия СУБД.
  - Testcontainers допустим для отдельного интеграционного набора (путь «API → очередь → воркер» с настоящим Redis), который запускается отдельной командой.
  - Kotest или JUnit 5: выбери.
- ktlint и detekt, сборка падает на нарушениях.
- Задачи Gradle или `Makefile`: `run-api`, `run-worker`, `test`, `integrationTest`, `lint`.
- Многоэтапный `Dockerfile` и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта с пояснением каждого модуля;
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение ключевых решений с Python- и Java-версиями.
  - Отдельно: как поэкспериментировать с классами интерактивно, по аналогии с `rails c` (например, Kotlin REPL или scratch-файлы IntelliJ).

## Как работать

1. Сначала предложи структуру модулей, выбор библиотек и подход к очереди. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты и линтеры.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
