# Задача: реализация backend на Ruby + Hanami

Сделай в папке `backend-hanami/` реализацию backend-сервиса на **Ruby и Hanami 2** (актуальная стабильная версия). Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Эту реализацию я буду сравнивать с Python-версией, с лёгкими Ruby-версиями на Sinatra и Roda и с остальными.

**Обо мне:** Ruby и Rails я знаю хорошо, Sidekiq тоже. Hanami мне интересен как полноценный фреймворк, построенный на других идеях, чем Rails:
- контейнер и внедрение зависимостей (`Deps`, providers) вместо глобальных объектов;
- action — отдельный класс на эндпоинт, а не метод контроллера;
- слои БД в духе Data Mapper (relations, repos, structs) вместо Active Record;
- slices как границы модулей.

Многое из этого мы в Python-версии делали руками: протоколы и `Depends`, репозиторий, отделение домена от ORM, `lifespan`. Поэтому:
- пиши идиоматичный Hanami и используй его механизмы там, где они решают задачу. Не тащи Rails-привычки (ActiveRecord, ActiveSupport, «толстые модели»). Каждую стороннюю зависимость обоснуй;
- в README сравни ключевые решения с тем, как это сделал бы Rails, и с Python-версией;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`;
  - невалидное тело или кривой `task_id` → `422`;
  - неизвестная задача → `404 {"detail": "Task not found"}`;
  - Postgres или Redis недоступен → `503 {"detail": "Storage is unavailable"}`.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_hanami`, тестовая — `analysis_hanami_test`.
- Номер БД Redis — `11` (`REDIS_URL=redis://localhost:6379/11`).
- Базу создаёт сам backend, если её нет. В Hanami для этого есть `hanami db create` / `hanami db prepare` — аналоги Rails-команд.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в Hanami, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (`hanami db prepare` или
  эквивалент), затем `api` и `worker`. Запуск: сначала `docker compose -f ../docker-compose.yml up -d`,
  потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код.

- **Только API**: без views, шаблонов и assets.
- **Структура: app и slices.** Домен анализа — slice или часть `app`: выбери и обоснуй для этого размера. Внешние клиенты (`youtube`, `llm`) — отдельные компоненты контейнера.
- **Actions.** По классу на эндпоинт, маршруты в `config/routes.rb`. Вход валидируется в action (`params` с dry-validation или contract). Невалидный вход отсекается до сервиса с `422`. Action знает только HTTP.
- **Слои и направление зависимостей:** `action → operation / service → repo / clients`.
  - Сервисы ничего не знают про HTTP, Rack, БД и Redis.
  - Зависимости приходят через `include Deps[...]` из контейнера. Покажи, как это выглядит в тестах: подмена зависимости в конструкторе и (если нужно) `stub` контейнера.
  - Бизнес-сценарии оформи как operations (dry-operation, `Success`/`Failure`) или обычные классы-сервисы: выбери и обоснуй.
- **Интерфейсы.** Формальных интерфейсов в Ruby нет, но порты всё равно должны быть видны: очередь, источник комментариев и классификатор описаны как роли с понятным контрактом (документация, тесты на соответствие или RBS — выбери). Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника (`CommentSourceError` в Python), поэтому сервис ничего не знает о клиенте.
- **Конфигурация** — `config/settings.rb` с типами: при ошибке приложение падает при загрузке с понятным сообщением. Без `ENV[...]` по всему коду. Создание базы и миграции не должны требовать ключей YouTube и LLM: проверь, как это совместить с настройками Hanami.
- **Ресурсы с жизненным циклом** (Redis, HTTP-клиент, LLM-клиент) — providers в `config/providers` с `prepare`/`start`/`stop`. Это аналог `lifespan` в FastAPI.
- **Ошибки:**
  - доменные ошибки переводятся в HTTP-коды в одном месте (`handle_exception` в базовом action или аналог);
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`.
- **Хранение задач — Postgres через слой БД Hanami** (relations, repos, structs). Таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`, `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет). Миграции — штатные Hanami. Redis — только очередь.
  - Repo возвращает structs, а не «живые» модели: это уже разделение домена и хранения, которое в Python пришлось делать вручную (`AnalysisTask` и `AnalysisTaskOrm`). Реши, достаточно ли struct как доменной сущности или нужен свой тип поверх него, и обоснуй.
  - Каждая операция repo — своя короткая транзакция: обработка задачи в воркере длится минутами, держать соединение всё это время незачем.
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - Встроенных фоновых задач в Hanami нет. Ожидаемый вариант — Sidekiq без ActiveJob. Воркер загружает приложение Hanami и берёт зависимости из того же контейнера.
  - Честно разбери гарантии. В Python-версии слабое место — `BRPOP`, который удаляет сообщение сразу при получении. В Sidekiq OSS то же самое: при жёстком падении процесса задача теряется, а надёжный `super_fetch` есть только в Pro. Предложи решение или явно задокументируй компромисс. Очередь на Postgres вместо Redis — допустимая альтернатива, если аргументируешь.
  - Нужны повторные попытки с ограничением, и задача после исчерпания попыток получает `failed`.
- **Внешние вызовы:**
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429), понятные ошибки для 404, 403 и 400, таймауты. Faraday с retry-middleware или HTTPX: выбери;
  - LLM: структурированный ответ по схеме с валидацией, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** (пул потоков `concurrent-ruby` или `async`: выбери и объясни).
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. Оцени `ruby_llm` или OpenAI-совместимый клиент с base URL. Держи провайдера за своим классом-адаптером.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала». Логи структурированные (JSON), через логгер Hanami.
- **Ожидание сообщений в очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Проверь, как с этим у `redis-client`, который использует Sidekiq.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения (relation, struct) — по соглашениям Hanami;
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенный комментарий.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.

## Инструменты и качество

- Актуальная стабильная версия Ruby, Bundler.
- Тесты на RSpec (стандарт генератора Hanami):
  - БД — настоящий Postgres из общей инфраструктуры (база `analysis_hanami_test`), как в Rails. Схема готовится миграциями перед прогоном, каждый тест изолирован транзакцией с откатом (используй то, что генерирует Hanami, или DatabaseCleaner). Если Postgres не запущен, прогон сразу останавливается с понятным сообщением. SQLite и in-memory подмены БД не используй;
  - YouTube через WebMock, фейки для источника комментариев, классификатора и очереди;
  - unit-тесты actions (вызов action напрямую) и request-тесты через `rack-test`;
  - `Sidekiq::Testing` для пути «API → очередь → воркер».
- RuboCop (или Standard), без замечаний.
- `hanami console` — прямой аналог `rails c`. Покажи в README, как получить из контейнера сервисы и клиентов и поэкспериментировать с ними.
- Команды: `hanami server` / `hanami dev`, запуск воркера, `hanami db prepare`, тесты, линтер. Через `bin/`, `Rakefile` или `Procfile.dev`: выбери.
- `Dockerfile` и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта (app, slices, providers, relations, repos);
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение с Rails (контейнер и `Deps` против глобальных объектов, actions против контроллеров, repos и structs против ActiveRecord, providers против инициализаторов);
  - сравнение с Python-версией: что в Hanami дал фреймворк из того, что там делали руками.

## Как работать

1. Сначала предложи структуру (app или slices), выбор гемов и подход к очереди. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты и линтер.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
