# Задача: реализация backend на .NET (ASP.NET Core)

Сделай в папке `backend-net/` реализацию backend-сервиса на **C# и ASP.NET Core**. Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель не в минимальном количестве кода, а в том, чтобы показать, как идиоматично устраивают такие сервисы в .NET. Эту реализацию я буду сравнивать с версиями на Python, Go, Node, Rust, Java и Kotlin.

**Обо мне:** я знаю Ruby/Rails (Sidekiq, `rails c`) и Python/FastAPI. .NET для меня новый. Поэтому:
- объясняй неочевидные решения коротко, в README и в комментариях, с аналогиями из Rails/FastAPI там, где они помогают:
  - Generic Host;
  - DI и время жизни сервисов (singleton/scoped/transient);
  - Options pattern;
  - middleware;
  - `async`/`await` и `CancellationToken`;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Поля JSON в `snake_case`. У `System.Text.Json` по умолчанию `camelCase`, настрой. Enum'ы сериализуются строками.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`. ASP.NET Core по умолчанию отдаёт `400`, поменяй;
  - кривой `task_id` → `422`;
  - неизвестная задача → `404`, в теле `"detail": "Task not found"`;
  - Postgres или Redis недоступен → `503`, в теле `"detail": "Storage is unavailable"`.

  Формат `ProblemDetails` (RFC 9457) допустим: поле `detail` там уже есть, дополнительные поля не мешают.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`. Плоские имена вроде `REDIS_URL` нужно явно связать с Options: стандартная схема .NET — `Section__Key`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_dotnet`, тестовая — `analysis_dotnet_test`.
- Номер БД Redis — `6` (`REDIS_URL=redis://localhost:6379/6`).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код: реализация должна выглядеть как нормальный современный .NET-проект.

- **Структура.** Solution с несколькими проектами, например:
  - `Domain/Core` без зависимостей от ASP.NET, БД и Redis;
  - `Infrastructure`;
  - `Api` (ASP.NET Core);
  - `Worker` (Worker Service на Generic Host);
  - тестовые проекты.

  Без тяжёлой «Clean Architecture» с десятком слоёв и MediatR ради самого паттерна: структура должна соответствовать размеру и быть готовой к росту. Если считаешь нужным иначе, предложи с обоснованием.
- **Организация по доменам** внутри проектов: `Analysis`, `YouTube`, `Llm`.
- **Слои и направление зависимостей:** `endpoint → service → repository / clients`.
  - Эндпоинт знает только HTTP.
  - Сервис ничего не знает про HTTP, БД и Redis.
  - Сервис зависит от **интерфейсов** (очередь задач, источник комментариев, классификатор, хранилище задач), зарегистрированных во встроенном DI.
  - Внимательно со временем жизни: singleton не должен зависеть от scoped.
- **HTTP.** Minimal APIs с группами маршрутов или контроллеры: выбери и обоснуй.
- **Модели.** `record` для DTO и значений, строгие типы для `TaskId` и `VideoId` там, где это не усложняет код. Nullable reference types включены. Внутренние модели отделены от DTO ответа.
- **Валидация на границе.** Вход проверяется до сервиса. Конфигурация через Options pattern с `ValidateDataAnnotations`/`ValidateOnStart`: приложение падает при старте с понятной ошибкой.
- **Ошибки:**
  - доменные исключения или result-типы переводятся в HTTP-коды в одном месте (`IExceptionHandler` / `ProblemDetails`);
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`.
- **Жизненный цикл.**
  - `CancellationToken` передаётся по всей цепочке;
  - graceful shutdown хоста;
  - `HttpClient` только через `IHttpClientFactory` / typed clients.
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - `BackgroundService` внутри API — это аналог `BackgroundTasks` из исходного примера, от которого мы ушли. Воркер — отдельный процесс, чтобы задачи переживали рестарт и деплой API, а API и обработка масштабировались независимо.
  - Задача не должна теряться при падении воркера. В Python-версии это слабое место: `BRPOP` удаляет сообщение сразу при получении.
  - Ожидаемый вариант — Redis Streams с consumer groups (ack, повторная доставка зависших сообщений). Учти, что StackExchange.Redis из-за мультиплексирования **не поддерживает блокирующие команды** (`BRPOP`, `XREADGROUP BLOCK`): нужен опрос с паузой или другое решение.
  - Если выберешь Hangfire или другую библиотеку, аргументируй.
  - Нужны повторные попытки с ограничением.
- **Хранение задач — Postgres**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`,
  `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет).
  Схема задаётся миграциями, принятыми в стеке. Библиотеку доступа к БД выбери и обоснуй, ориентиры: EF Core + Npgsql (миграции `dotnet ef`) или Dapper.
  Redis — только очередь.
  - Доменная сущность отделена от модели хранения: сервисы работают с доменной `AnalysisTask`
    и не знают о БД, репозиторий переводит её в модель хранения и обратно.
  - Каждая операция репозитория — своя короткая транзакция: обработка задачи в воркере длится
    минутами, держать соединение всё это время незачем.
- **Внешние вызовы:**
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429; `Microsoft.Extensions.Http.Resilience`/Polly), понятные ошибки для 404, 403 и 400, таймауты;
  - LLM: структурированный ответ по схеме с валидацией, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** (`Parallel.ForEachAsync` или `SemaphoreSlim`).
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. Оцени `Microsoft.Extensions.AI` (`IChatClient` со структурированным выводом) поверх OpenAI-совместимого клиента с настраиваемым endpoint. Держи провайдера за абстракцией.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала». Структурированное логирование через `ILogger` с message templates, `task_id` в logging scope. Serilog по желанию, с обоснованием.
- **Ожидание сообщений в очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Для StackExchange.Redis это превращается в вопрос правильного цикла опроса, см. выше.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда. В .NET по умолчанию `.env` не читается вообще: реши, как подгружать его локально.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом (в Python — `AnalysisTaskOrm`);
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенная `CommentSchema`.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
  Если в стеке принят другой суффикс, следуй ему, но единообразно.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот.
  Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника
  (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены
  отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальная LTS-версия .NET.
- `Directory.Build.props` с общими настройками: nullable, `TreatWarningsAsErrors`, анализаторы. Central Package Management.
- Библиотеки выбирай сам, предпочитая встроенное в платформу. Каждый выбор кратко обоснуй в README.
- Тесты (xUnit):
  - **основной набор** (YouTube, LLM и очередь подменяются): unit-тесты разбора URL, клиента YouTube (фейковый `HttpMessageHandler` или WireMock.Net), сервиса (с фейками интерфейсов), группировки результатов; HTTP через `WebApplicationFactory` с подменой сервисов;
  - БД в тестах — настоящий Postgres из общей инфраструктуры (база `analysis_dotnet_test`), как в Rails.
    Схема накатывается миграциями один раз на прогон (заодно проверяются сами миграции), каждый тест
    выполняется в транзакции с откатом. Если Postgres не запущен, прогон сразу останавливается
    с понятным сообщением. SQLite и in-memory подмены БД не используй: они скрывают различия СУБД.
  - Testcontainers допустим для отдельного интеграционного набора (путь «API → очередь → воркер» с настоящим Redis), который запускается отдельно.
- `dotnet format` без замечаний.
- `Makefile` или скрипты: `run-api`, `run-worker`, `test`, `lint`.
- Многоэтапный `Dockerfile` для каждого приложения и `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»). .NET Aspire для локальной оркестрации можно предложить как дополнение, не вместо compose.
- `.gitignore`.
- README:
  - структура solution с пояснением каждого проекта;
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение ключевых решений с Python-версией.
  - Отдельно: как поэкспериментировать с классами интерактивно, по аналогии с `rails c` (например, `csharprepl` с подключёнными сборками проекта или Polyglot Notebooks).

## Как работать

1. Сначала предложи структуру solution, выбор библиотек и подход к очереди. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты и `dotnet format`.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
