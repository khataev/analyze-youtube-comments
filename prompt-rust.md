# Задача: реализация backend на Rust

Сделай в папке `backend-rust/` реализацию backend-сервиса на Rust. Она должна быть функционально эквивалентна эталонной реализации на Python из `../backend-python/`. Прочитай её код и README перед началом.

Проект простой, но структуру строй как для среднего или крупного проекта, который будет развиваться. Цель не в минимальном количестве кода, а в том, чтобы показать, как идиоматично устраивают такие сервисы в Rust. Эту реализацию я буду сравнивать с Python-, Go- и Node-версиями.

**Обо мне:** в Rust я новичок. Я знаю Ruby/Rails (Sidekiq, `rails c`) и Python/FastAPI. Поэтому:
- объясняй неочевидные для Rust решения коротко, в README и в комментариях, с аналогиями из Ruby/Python там, где они помогают. Особенно:
  - владение и заимствование там, где оно влияет на дизайн (`Arc`, клонирование клиентов);
  - `Result` и оператор `?`;
  - трейты как интерфейсы;
  - async и tokio;
- не усложняй ради «красоты» типов: если выбор между обобщёнными параметрами и `dyn Trait` не принципиален, предпочитай читаемость и объясни компромисс;
- перед крупным отступлением от этого промпта спроси меня.

## Что делает сервис

Принимает ссылку на YouTube-видео, загружает комментарии через YouTube Data API, классифицирует их через LLM и отдаёт результат, сгруппированный по категориям. Обработка долгая, поэтому идёт асинхронно: клиент получает `task_id` и опрашивает статус.

## Контракт (должен совпадать с Python-версией, его использует общий фронтенд)

| Метод | Путь | Ответ |
|---|---|---|
| `POST` | `/api/v1/analysis`, тело `{"url": "..."}` | `202 {"task_id": "<uuid>"}` |
| `GET` | `/api/v1/analysis/{task_id}` | `200 {"task_id", "status", "result", "error"}` |
| `GET` | `/health` | `200 {"status": "ok"}` или `503`, если Postgres или Redis недоступен |

- `status`: `pending` → `processing` → `completed` или `failed`.
- `result`: `{"<Category>": [{"id", "text"}, ...]}`. Пустые категории не выводятся.
- Категории (строки именно такие): `Video suggestion`, `Questions`, `Thanks`, `Advice/tips`, `Corrections`, `Summaries`, `Bots`, `Feedback`.
- Ошибки:
  - невалидный URL или не-YouTube ссылка → `422`;
  - кривой `task_id` → `422`;
  - неизвестная задача → `404 {"detail": "Task not found"}`;
  - Postgres или Redis недоступен → `503 {"detail": "Storage is unavailable"}`.

  Ошибки извлечения тела и пути в axum по умолчанию отдают свои коды и текст: приведи их к контракту.
- Поддерживаемые форматы ссылок: `youtube.com/watch?v=`, `youtu.be/<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`.
- Конфигурация задаётся теми же переменными окружения, что в `../backend-python/.env.example`. Нужен свой `.env.example`.

## Общая инфраструктура

Redis и Postgres общие для всех реализаций и описаны в `../docker-compose.yml`: сеть `ayc-infra`,
пользователь и пароль `app`, порты `6379` и `5432` на localhost. Свои контейнеры Redis и Postgres
не поднимай. Распределение баз между реализациями — в `../README.md`.

- Твоя база Postgres — `analysis_rust`, тестовая — `analysis_rust_test`.
- Номер БД Redis — `3` (`REDIS_URL=redis://localhost:6379/3`).
- Базу создаёт сам backend, если её нет, — аналог `rails db:create` (в Python-версии это
  `python -m app.db.create`). Init-скриптов в общей инфраструктуре нет намеренно,
  а `CREATE DATABASE IF NOT EXISTS` в Postgres не существует.
- `DATABASE_URL` в Python-версии записан в формате SQLAlchemy (`postgresql+asyncpg://...`).
  Используй формат, принятый в твоём стеке, и укажи его в `.env.example`.
- Свой `docker-compose.yml` подключается к сети `ayc-infra` как к внешней (`external: true`)
  и содержит только сервисы этого backend: одноразовый `migrate` (создать базу и применить
  миграции; аналог `rails db:prepare`), затем `api` и `worker`. Запуск: сначала
  `docker compose -f ../docker-compose.yml up -d`, потом `docker compose up`.

## Архитектура и принципы

Перенеси идеи эталона, а не его код: реализация должна выглядеть как нормальный Rust-проект.

- **Структура.** Cargo workspace с несколькими крейтами, например:
  - доменная логика без зависимостей от HTTP, БД и Redis;
  - инфраструктура (БД, Redis, клиенты YouTube и LLM);
  - бинарники `api` и `worker`.

  Если для этого размера считаешь workspace избыточным, предложи альтернативу с обоснованием.
- **Слои и направление зависимостей:** `axum handler → service → repository / clients`.
  - Хендлер знает только HTTP.
  - Сервис ничего не знает про HTTP, БД и Redis.
  - Сервис зависит от **трейтов** (очередь задач, источник комментариев, классификатор, хранилище задач). В тестах их подменяют фейками.
- **Организация по доменам:** модуль `analysis` содержит свои handlers, service, repository и задачи. Внешние клиенты (`youtube`, `llm`) вынесены отдельно.
- **Сборка зависимостей явно в `main`** (composition root). Общее состояние передаётся через `State` в axum, без глобальных переменных и без DI-фреймворков.
- **Типы на границе («parse, don't validate»):** `VideoId`, `TaskId`, enum статусов и категорий с serde-представлением строго по контракту. Невалидное состояние должно быть непредставимо там, где это не усложняет код.
- **Ошибки:**
  - доменные ошибки через `thiserror`;
  - `anyhow` допустим только на краях (в `main` и инициализации);
  - один тип ошибки приложения с `IntoResponse` переводит их в HTTP-коды;
  - внутренние детали не утекают клиенту;
  - упавшая задача получает статус `failed` с понятным сообщением и никогда не зависает в `processing`. В том числе при панике внутри обработки.
- **Жизненный цикл:**
  - конфигурация читается и валидируется при старте, при ошибке процесс падает сразу с понятным сообщением;
  - ресурсы создаются один раз;
  - graceful shutdown по SIGTERM и Ctrl+C;
  - воркер дожидается текущих задач или корректно их возвращает в очередь.
- **Фоновая обработка — отдельный процесс-воркер с очередью в Redis.**
  - В Rust нет единого стандарта уровня Sidekiq. Предложи вариант и обоснуй его, например:
    - `apalis` с Redis-хранилищем;
    - собственная небольшая очередь на Redis Streams с consumer groups (`XREADGROUP` / `XACK` / `XAUTOCLAIM`).
  - Обязательное требование: задача не теряется при падении воркера. В Python-версии это слабое место: `BRPOP` удаляет сообщение сразу при получении. Нужны повторные попытки с ограничением.
  - Отдельный воркер нужен не ради асинхронности (tokio справится и в одном процессе). Он нужен ради надёжности: задачи переживают рестарт и деплой API, API и обработка масштабируются независимо.
- **Хранение задач — Postgres**, таблица `analysis_tasks`: `id` (uuid), `video_id`, `status`,
  `result` (`jsonb`), `error`, `created_at`, `updated_at`. Записи хранятся бессрочно (TTL нет).
  Схема задаётся миграциями, принятыми в стеке. Библиотеку доступа к БД выбери и обоснуй, ориентиры: `sqlx` (проверка запросов на этапе компиляции, встроенные миграции и `sqlx database create`) или SeaORM.
  Redis — только очередь.
  - Доменная сущность отделена от модели хранения: сервисы работают с доменной `AnalysisTask`
    и не знают о БД, репозиторий переводит её в модель хранения и обратно.
  - Каждая операция репозитория — своя короткая транзакция: обработка задачи в воркере длится
    минутами, держать соединение всё это время незачем.
- **Внешние вызовы:**
  - YouTube: пагинация до лимита `YOUTUBE_MAX_COMMENTS`, повторные попытки с backoff только для временных ошибок (сеть, 5xx, 429), понятные ошибки для 404, 403 и 400, общий `reqwest::Client` с таймаутами;
  - LLM: структурированный ответ по JSON-схеме с проверкой через serde, комментарии разбиваются на батчи (`LLM_BATCH_SIZE`).
  - Батчи обрабатываются параллельно с **ограничением** числа одновременных запросов (`buffer_unordered` или семафор).
- **LLM-провайдер настраиваемый:** `LLM_MODEL` в формате `provider:model`, например `deepseek:deepseek-chat`, ключ в `LLM_API_KEY`. DeepSeek совместим с OpenAI API, так что достаточно OpenAI-совместимого клиента с настраиваемым base URL. Держи провайдера за трейтом.

## Что мы уже выучили на Python-версии (учесть сразу)

- **Ключ API передавать в заголовке**, а не в query: иначе он попадёт в логи и тексты ошибок. Пароли в `REDIS_URL` и `DATABASE_URL` в логах маскировать. Секреты в конфигурации хранить в обёртке, которая не печатается в `Debug`, например `secrecy`.
- **Текст комментариев — недоверенные данные.** Передавать их в LLM как JSON, в промпте запретить выполнять инструкции из комментариев. Отбрасывать выдуманные моделью и повторяющиеся `id`.
- **Логировать каждый этап с `task_id`:**
  - API: создана, поставлена в очередь;
  - воркер: получена, загрузка комментариев, батчи LLM с длительностью и токенами, сохранение, итог или ошибка;
  - при старте API и воркера: к каким Redis и Postgres подключились (пароль замаскирован) и какую очередь слушают.

  Это позволяет сразу отличить «воркер не запущен» от «задача упала». Используй `tracing` со span'ами на задачу.
- **Блокирующее ожидание очереди** не должно падать по таймауту чтения соединения. В Python так и случилось: redis-py 8 по умолчанию рвёт чтение через 5 секунд. Проверь таймауты ответа выбранного Redis-клиента для блокирующих команд и покрой поведение тестом или явным комментарием.
- **Запуск не должен зависеть от текущего каталога:** `.env` должен находиться независимо от того, откуда запущена команда.
- **Три представления одной сущности — три типа с единым шаблоном имён:**
  - доменная сущность с чистым именем — `AnalysisTask`;
  - модель хранения с суффиксом (в Python — `AnalysisTaskOrm`);
  - схемы API по роли: `AnalyzeRequest`, `TaskCreatedResponse`, `TaskStatusResponse`, вложенная `CommentSchema`.

  Слова «record» и «row» для доменных объектов не используй: в терминах БД это синонимы строки.
  Если в стеке принят другой суффикс, следуй ему, но единообразно.
- **Интерфейсы объявляет потребитель** (доменный слой), а реализации зависят от домена, не наоборот.
  Клиент YouTube возвращает доменный `Comment` и бросает доменную ошибку источника
  (`CommentSourceError` в Python), поэтому сервис ничего не импортирует из клиента.
- **Миграциям и созданию базы не нужны ключи YouTube и LLM.** В Python для этого выделены
  отдельные настройки только с `DATABASE_URL`.

## Инструменты и качество

- Актуальная стабильная версия Rust, edition 2024.
- Библиотеки выбирай сам, предпочитая общепринятые решения. Каждый выбор кратко обоснуй в README. Ориентиры для оценки, а не требование:
  - `tokio`, `axum`, `tower-http` (CORS, трассировка, таймауты);
  - `serde`, `tracing`;
  - `reqwest`;
  - `redis` или `fred`;
  - `thiserror` и `anyhow`.
- **Тесты.** YouTube, LLM и очередь подменяются. БД в тестах — настоящий Postgres из общей инфраструктуры (база `analysis_rust_test`), как в Rails.
  Схема накатывается миграциями один раз на прогон (заодно проверяются сами миграции), каждый тест
  выполняется в транзакции с откатом. Если Postgres не запущен, прогон сразу останавливается
  с понятным сообщением. SQLite и in-memory подмены БД не используй: они скрывают различия СУБД.

  Наборы:
  - unit-тесты разбора URL, клиента YouTube (например, `wiremock`), сервиса (с фейками трейтов), группировки результатов;
  - интеграционный тест HTTP API через `tower::ServiceExt::oneshot`;
  - тест пути «API → очередь → воркер».
- `cargo clippy -- -D warnings` и `cargo fmt --check` без замечаний. По возможности `cargo deny` или `cargo audit`.
- `justfile` или `Makefile` с командами: `run-api`, `run-worker`, `test`, `lint`.
- Многоэтапный `Dockerfile` с кэшированием зависимостей (например, `cargo-chef`) и минимальным итоговым образом. `docker-compose.yml` только с сервисами этого backend: migrate + api + worker (см. «Общая инфраструктура»).
- `.gitignore`.
- README:
  - структура проекта с пояснением каждого крейта и модуля;
  - как запустить локально и в Docker;
  - как проверить;
  - сравнение ключевых решений с Python-версией.

## Как работать

1. Сначала предложи структуру workspace, выбор библиотек и подход к очереди. Дождись моего согласия.
2. Затем реализуй по слоям, прогоняя тесты и clippy.
3. В конце проверь живой запуск: API + воркер + Redis + Postgres, задача доходит до финального статуса. Покажи логи.
